# Phase 2: Foundation & data model

## Overview
Create the database tables the admin (Phase 3) and public page (Phase 4) both depend on. Schema `church_donations` (local: `personal_projects` DB; Neon: own DB, same schema name). Migrations are timestamped `.sql` files in `migrations/`, applied with `npm run migrate`. DB plumbing (`lib/db.js`, `scripts/migrate.js`) and the auth shell already exist from setup.

## Scope

### Included
- Migration creating the tables below, plus seeds for `site_settings` keys
- `lib/` query helpers for the shared reads (item list with pledged/remaining, donation list) so both phases reuse them
- Optional `npm run seed` with a couple of demo items for local dev only

### Not included
- Any UI (Phase 3 and 4)
- Partial payments / installments — a donation is simply pending, received or cancelled
- Users table — auth is a single shared credential (`.env`)

## Migration SQL
File: `migrations/20260925_create_donation_tables.sql` (date = the day it's written). Runs inside the schema set by `PGSCHEMA` via `search_path`, so no schema prefix in the SQL.
```sql
CREATE TABLE items (
  id SERIAL PRIMARY KEY,
  name TEXT NOT NULL CHECK (length(btrim(name)) BETWEEN 1 AND 100),
  unit_price_crc INTEGER NOT NULL CHECK (unit_price_crc > 0),
  goal_quantity INTEGER CHECK (goal_quantity IS NULL OR goal_quantity > 0),  -- NULL = no goal / no countdown
  active BOOLEAN NOT NULL DEFAULT true,
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE donations (
  id SERIAL PRIMARY KEY,
  client_token UUID NOT NULL UNIQUE,   -- generated by the browser per form; makes double-submit idempotent (Phase 4)
  donor_name TEXT NOT NULL CHECK (length(btrim(donor_name)) BETWEEN 1 AND 100),
  donor_phone TEXT NOT NULL CHECK (donor_phone ~ '^[0-9]{8}$'),
  total_crc INTEGER NOT NULL CHECK (total_crc > 0),
  status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','received','cancelled')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  status_changed_at TIMESTAMPTZ
);
CREATE INDEX idx_donations_status_created ON donations (status, created_at DESC);

CREATE TABLE donation_items (
  id SERIAL PRIMARY KEY,
  donation_id INTEGER NOT NULL REFERENCES donations(id) ON DELETE CASCADE,
  item_id INTEGER NOT NULL REFERENCES items(id),          -- no cascade: items are deactivated, never deleted
  quantity INTEGER NOT NULL CHECK (quantity BETWEEN 1 AND 9999),
  unit_price_crc INTEGER NOT NULL CHECK (unit_price_crc > 0),  -- copied from items at pledge time
  UNIQUE (donation_id, item_id)
);
CREATE INDEX idx_donation_items_item ON donation_items (item_id);

CREATE TABLE site_settings (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL DEFAULT '',
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
INSERT INTO site_settings (key, value) VALUES
  ('welcome_message', 'Bienvenido. "Cada uno dé como propuso en su corazón, no con tristeza ni por necesidad, porque Dios ama al dador alegre." — 2 Corintios 9:7'),
  ('payment_instructions', '¡Gracias por tu compromiso! Puedes entregar tu aporte en efectivo a un hermano de la iglesia o por SINPE Móvil.'),
  ('sinpe_number', '');
```
Notes:
- Status is on the **whole donation**, not per line. Allowed transitions (enforced in the API in Phase 3, not in SQL): `pending → received`, `pending → cancelled`, `received → cancelled`. `cancelled` is final.
- Deleting is never done from the app. `ON DELETE CASCADE` on `donation_items` only helps manual cleanup in dev.
- `sinpe_number` is seeded empty; the public thank-you screen hides the SINPE line while it's empty.
- Local demo data (dev only): `scripts/seed.js`, run with `npm run seed`, inserts 3 items and a few donations in mixed statuses. Never runs against production.

## Shared query helpers (`lib/donations.js`)
Both the admin and the public page must use these — never re-implement the counter elsewhere.
```sql
-- Items with counters. `remaining` is computed in JS: goal == null ? null : Math.max(goal - pledged, 0)
SELECT i.id, i.name, i.unit_price_crc, i.goal_quantity, i.active, i.sort_order,
       COALESCE(SUM(di.quantity) FILTER (WHERE d.status IN ('pending','received')), 0)::int AS pledged
FROM items i
LEFT JOIN donation_items di ON di.item_id = i.id
LEFT JOIN donations d ON d.id = di.donation_id
GROUP BY i.id
ORDER BY i.sort_order, i.id;
```
Helpers to export: `listItemsWithCounters({ activeOnly })`, `createDonation(...)` (one transaction; see Phase 4 for rules), `listDonations({ status, itemId, search, sort, order, limit, offset })` returning `{ items, total }`, `setDonationStatus(id, next)` (see Phase 3), `getSettings()` / `updateSettings()`.
Lists of donations must also return each donation's lines (`item name, quantity, unit_price_crc`) — aggregate with `json_agg` in the same query to avoid N+1.

## Price changes
Editing `items.unit_price_crc` only affects **new** pledges. Each `donation_items.unit_price_crc` keeps the price at the time of the pledge, so old totals never change. No price-history table needed.

## Counter rule (shared by admin and public page)
`pledged(item) = SUM(donation_items.quantity)` over donations with status `pending` or `received`.
`remaining(item) = MAX(goal_quantity − pledged, 0)`. Over-goal pledging is allowed; the admin raises `goal_quantity` if wanted. Cancelling a donation gives its units back.
